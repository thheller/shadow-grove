# Examples

The shadow-grove documentation, written as examples. Each example covers one concept.
It is a namespace in `src/dev/examples/` that reads like a document: prose in
comments, then the code it explains. The same file is a page you can try in the
browser, showing the text, a live demo and the code. A browser scenario checks that
the page does what its text says.

The other folders in `examples/` are older experiments and benchmarks, not part of
this set.

## Where to read what

Start with `src/dev/examples/overview.cljs`: the five pieces, one interaction end to
end, bootstrap, and a "where does this belong" list pointing to the other examples.

| topic | examples |
|---|---|
| components | `defc_basics`, `stable_args`, `refs`, `local_state`, `effects`, `bind_helpers`, `component_events`, `animations` |
| markup | `markup`, `dom_events`, `lists`, `suspense`, `portal`, `lazy_loading`, `edn_view` |
| data | `kv_reads`, `kv_writes`, `loading_sentinel` |
| changing data | `transactions` (+ `transactions_test`), `fx`, `forms`, `keyboard`, `external_events` |
| routing | `routing`, `hash_routing`, `auth_gate` |
| server data | `http_fx`, `http_pull`, `websocket` |
| large lists | `vlist`, `vlist_remote` |
| custom managed nodes | `widget_node`, `child_host`, `async_node`, `custom_attributes`, `slot_provider`, `signals` |

## How a file becomes a page

`(c/page "title" {"chapter title" demo ...})` in an example's root component is a macro
(`src/dev/examples/common.clj`). At compile time it reads the example's own source:

- the ns docstring is the intro
- `;; ## title` starts a chapter, which runs until the next `;; #` or `;; ##` line
- in a chapter, the first comment block is prose, and so is any later comment block
  followed by a blank line. A comment block directly above a form belongs to that form
- everything else in the chapter is shown as code
- `;; # page` starts the page's own wiring (`ui-root`, `init`), which isn't shown

Prose is a small markdown subset: paragraphs, `- ` bullets (continued with two
spaces), `### ` subheadings, fenced code, pipe tables, `code`, **bold**, and
`[links](/other-example/#chapter)`. Each demo goes after its chapter's first prose
block. A demo whose chapter doesn't exist is a compile error. Chapters without a demo
are prose and code only.

## Layout

```
src/dev/examples/<name>.cljs        one namespace per example, ns examples.<name>
src/dev/examples/common.cljs        page chrome, render counters, log panel
src/dev/examples/common.clj         the page macro: source -> intro, chapters, code
src/dev/examples/server.clj         dev-http handler: pushState fallback + small fake APIs
examples/public/index.html          overview of all examples
examples/public/<name>/index.html   the page, loads /js/<name>.js and /css/<name>.css
examples/public/js/                 :examples build output (generated)
examples/public/css/                one CSS file per example (generated by src/dev/build.clj)
examples/test/run.mjs               runs the scenarios in headless chromium
examples/test/scenarios/<name>.mjs  one scenario per example
```

All examples are modules of the single `:examples` build (`:target :esm`).
`:shared` holds `examples.common`, and shadow-cljs moves code used by several
examples into it. Every other module depends on `:shared` and has its example's
`init` as `:init-fn`, so a page only loads its own module. `:lazy-loading-heavy` is
the one extra module, loaded on demand by the lazy-loading example.

## Running

The shadow-cljs server provides one dev-http on port 3020 for all examples
(`shadow-cljs.edn`):

```
npx shadow-cljs watch examples
```

then open http://localhost:3020/. `signals` requires `town.lilac/flex`, which only the
`:dev` alias in `deps.edn` provides, so the server has to run with that alias. With the
server started from the REPL
(`repl/start`), CSS is regenerated on file changes. Otherwise run
`(build/css-release)` from `src/dev/build.clj` once.

Examples that need a backend (`http-fx`, `http-pull`, `auth-gate`, `vlist-remote`)
talk to `/<name>/api/...`, served from atoms in `src/dev/examples/server.clj`. Its
`latency` atom adds a delay per example so loading states are visible.
`POST /<any>/api/reset` resets all of them. pushState routes such as
`/routing/item/1` survive a reload because the handler serves the example's
`index.html` for unknown paths below it.

`websocket` opens a real socket to `/websocket/api/ws`, also in `server.clj`. Every open
tab is one client. `POST /<any>/api/reset` doesn't touch it, it only holds live
connections.

After changing `common.clj`, delete `.shadow-cljs/builds/examples/dev/ana/examples/`
before compiling: the compile cache doesn't know the examples depend on the macro's
output format.

## Checking

```
node examples/test/run.mjs              all scenarios
node examples/test/run.mjs lists forms  only these
```

Needs the dev-http on 3020 and a compiled `:examples` build. `CHROME` and `BASE` env
vars override the browser binary and URL.

- A scenario fails on a failed `t.assert`, or on any `console.error` or uncaught
  exception it didn't announce with `t.expectConsoleError(/.../)`.
- The runner hides the prose and code (`[data-doc]`), so text checks only see the
  demos.
- `t.knownIssue(observed, "...")` records a library issue the example's text
  describes as a known issue. While it is observed it is listed under "known issues"
  at the end. Once it isn't (the issue got fixed), the scenario fails, so the text
  gets updated together with the fix.
- Most checks read the log panel (`examples.common/log!`) and the `× n` render badges
  (`(c/render-count key)` in a render), which make visible which binds, effects and
  renders ran. Both are testing aids, the page says so where they appear.

Tx handlers and queries are tested without a DOM in the `:examples-test` build:

```
npx shadow-cljs compile examples-test && node out/examples-test/test.js
```

## Adding an example

1. `src/dev/examples/<name>.cljs`: an ns docstring introducing the concept, `;; ##`
   chapters with prose and the code they explain, then `;; # page` with a `ui-root`
   rendering `(c/page "title" {"chapter" demo})`, `init` and a `^:dev/after-load`
   fn calling `c/render!`.
2. A module in the `:examples` build:
   `:<name> {:init-fn examples.<name>/init :depends-on #{:shared}}`.
3. `examples/public/<name>/index.html`, a copy of another example's page with the
   name replaced.
4. A link in `examples/public/index.html`, and the table above.
5. `examples/test/scenarios/<name>.mjs`, checking what the text claims.

Keep each example to one concept with neutral data. State what the library does on
master, and mark what doesn't work yet as a known issue with a `t.knownIssue` check.
