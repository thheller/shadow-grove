diff-seq benchmarks

A simple-seq that uses each item as its own key, plus a keyed-seq rebuilt on the same algorithm, measured against the current implementations at list sizes from 1 to 1000.

Headless Chromium 156 · arm64 Linux · release build · fragment rows · times are µs per update, median of 7 batches

Summary

Removing one item from a simple-seq makes every following row render its neighbour's data. diff-seq keeps the simple-seq API but uses the item itself as its key. It compares the old and new list from both ends with identical?, which handles inserts, removes, swaps, single moves and in-place updates without any lookup structure, and only builds a lookup for real reorders. The same code with a key-fn is a drop-in keyed-seq replacement, and it was faster than the current one everywhere it was measured.

9×remove first, 100 rows, incl. layout

Removing or inserting near the front of 100 rows takes 104 µs instead of 935 µs, with 0.5 renders and 2 DOM mutations per update instead of 99.5 and 464. The gain starts at 2 items (1.4×) and reaches 13× at 1000 rows. Removing from the middle is 4.8× faster at 100 rows.

1.0–22×keyed-seq new vs keyed-seq, script time

The rebuilt keyed-seq was faster than the current one in every scenario and size. The only exceptions are a few cells at 1–3 items, 0.94–0.99×, which is within noise. The current one rebuilds a persistent map of all keys on every update, about 155 µs at 1000 rows even when one row changes; the new one takes 7 µs there. Including layout the gain is 1.0–1.3×, because both make the same DOM changes.

1–5 itemssmall lists

At these sizes every implementation costs 0.2–5 µs of script and 12–70 µs including layout per update. diff-seq already wins removals and inserts at 2 items, 1.4–2.5× including layout. It loses on swaps and reverses once layout is counted, about 0.73× (a swap in 5 rows takes 42 µs instead of 31). For in-place updates it is a fraction of a microsecond slower in script time.

0.68×reverse, 1000 rows, incl. layout

Moving DOM costs more layout than rewriting text. Reverses, shuffles and swaps are faster with simple-seq once layout counts (reverse at 1000 rows: 10.2 ms vs 14.8 ms), and the same holds for both keyed implementations. Moves still keep per-row DOM state such as focus and input values.

8.6×fresh equal maps, 1000 rows

Identity matching misses maps that a query builds fresh on every run, so diff-seq then does what simple-seq does plus a lookup. diff-seq-by-value matches them with = and is 8.6× faster there in script time (90 vs 777 µs; 0.92 vs 9.7 ms with layout). Elsewhere = costs up to 10% more script time, more for in-place updates: 1.8× for one changed row in a small list (under 0.3 µs) and 1.5× when every 10th row changes (17 µs at 1000 rows). Layout hides both.

6.6×matching 1000 shuffled maps

The Map + Set proposal works, but a JS Map with duplicates chained in an Int32Array is 6.6× cheaper (37 vs 242 µs). The savings come from not allocating a Set per value and not hashing through a CLJS map. Both costs are small next to the 14 ms of moves and layout a 1000-row shuffle takes.

How diff-seq syncs a list

Every item has a key. Steps 1 to 4 run in a loop on the part of the list that is still unresolved, and only step 5 needs a lookup structure. Most edits never get there.

  1. Skip matching heads, then matching tails

    Compare old and new from the front while keys match, then from the back. Single inserts and removes anywhere, appends, prepends and single in-place updates all end here.

    [a b c d] → [a c d]
    head a · tails c d
    old middle [b], new middle []

  2. One side empty: insert or remove

    If the old middle is empty the new items are created before the first tail item. If the new middle is empty the old ones are destroyed. No renders for anything else.

    old middle [b] → destroy b
    0 renders, 2 DOM mutations

  3. Old head is new tail, or old tail is new head: move it

    Checks both crossings and moves the one DOM item, then goes back to step 1. Swaps, rotations and single moves resolve with identical? checks only.

    [1 2 3 4 5] → [1 5 3 4 2]
    2 is new tail: move
    5 is new head: move
    3 4 match as heads

  4. Unkeyed only: render over in place

    If the heads differ but the next pair matches, render the new head over the old head, which is what simple-seq does. Same for tails. Scattered updates stay linear. Keyed mode skips this step so a key's DOM never shows another key.

    [a B c D e] (B, D updated)
    a matches · B≠b, c=c → render
    c matches · D≠d, e=e → render

  5. General case: lookup, match, minimal moves

    A JS Map from key to the first unclaimed old index, with duplicate keys chained through an Int32Array. Unmatched new items render over unmatched old ones in order (unkeyed only). Leftovers are created or destroyed. The longest increasing subsequence of reused items stays put and the rest move.

    old [x y x], new [x x y]
    Map x→0 (chain 0→2), y→1
    new x→0, x→2, y→1
    sources [0 2 1], LIS keeps 0 1

Matching cost: Map + Set or something cheaper

The lookup only runs for real reorders (step 5). This measures it alone, without any DOM: build the lookup from the old items and match every new item. The proposal from the start of this exploration keys a CLJS map by item value and keeps a js/Set of indexes per value so duplicates work.

Reading the heatmaps

  • Removals and inserts away from the end are where diff-seq pays off, from 2 items up. simple-seq renders every following row over its neighbour; diff-seq destroys or creates one row.
  • simple-seq's own best cases (append, remove last, update one row, update every 10th) cost diff-seq up to about 1.5× more script time, because it also builds a new item array. With layout counted they are even.
  • Full reorders and swaps turn red in the first heatmap once layout is counted. Moving a row costs more layout than rewriting its text, and both keyed implementations move rows too (compare either against simple-seq in the third heatmap). In script time alone they are within about 25% either way.
  • Fresh equal maps defeat identity matching, so diff-seq does what simple-seq does plus a lookup. Pick diff-seq = as the candidate in the third heatmap to see the = mode remove that cost.
  • keyed-seq new vs keyed-seq is blue or neutral everywhere, by up to 22× in script time at 1000 rows. The gap with layout is smaller, 1.0–1.3×, because both create and move the same DOM.
  • keyed-seq new vs diff-seq (pick them in the third heatmap): the same speed, except "replace all", where keyed mode destroys and creates every row instead of rendering over them (3.5–4× slower), and fresh maps, where keys still match and identity does not.

Decisions for you

None of this is wired into shadow.grove yet, and the existing simple-seq and keyed-seq are unchanged.

  • Replace the keyed-seq implementation?

    diff-keyed-seq keeps the keyed-seq contract: same arguments, the render fn gets [item idx key], a key's DOM is never reused for another key, and items with identical data skip rendering. It was faster than the current implementation in every measured scenario and size. The one behavior change: duplicate keys throw only in dev builds. Checking them in release would mean building the full key set on every update, which is most of what makes the current version slow.

    Recommendation: put it behind sg/keyed-seq after trying it in a real app, and keep the dev-only duplicate check.

  • Default matching for the unkeyed version: identical? or =

    Identity is cheapest when list items are shared between renders, which is the case for vectors updated with conj, assoc or into, and for ids, strings and numbers. It misses maps that a query builds fresh on every run. = catches those, and costs little elsewhere because = returns early for identical items. Its risk is large, freshly built items, where every update pays a full hash and a deep comparison per item.

    Recommendation: = as the default, with identity available for hot lists of shared items.

  • What the render fn receives

    Matched items are not re-rendered, so the idx they saw can be out of date after a move. The current keyed-seq already behaves this way. A simple-seq render fn that uses idx for numbering or striping would break without any error if switched to diff-seq. Re-rendering whenever the index changes would bring back the cost diff-seq exists to remove.

    Recommendation: call the unkeyed render fn with just the item, so lists that need the index stay on simple-seq. Keep [item idx key] for the keyed version for compatibility.

  • Where simple-seq still fits

    simple-seq stays about 1.5× cheaper in script time for appends, removing the last item and in-place updates. It is also faster for full reorders once layout is counted, because rewriting text in place costs less layout than moving nodes. Neither difference is visible next to layout for appends and updates, but the reorder one is.

    Recommendation: keep simple-seq as is, and point the docs at diff-seq for any list that inserts or removes in the middle.

  • Names

    diff-seq, diff-seq-by-value and diff-keyed-seq are working names in shadow.arborist.collections. All three are one deftype with a mode, so the public surface can be any split you like, for example (sg/seq coll render-fn) with an option for identity.

Method and caveats

  • Rows are << fragments with 4 dynamic slots (tr class, id, link href and label, count) in a table attached to the document. Items are maps {:id :label :href :count :done}. No defc rows: those need a runtime, and component arg comparison would make rendering over a little cheaper.
  • Each implementation is called through its public function on a fresh root. Calibration picks a batch size of about 25 ms, then one warmup batch, then 7 timed batches with gc() before each. The reported value is the median batch divided by its update count.
  • "incl. forced layout" calls getBoundingClientRect() on the table after every update. An earlier run used .offsetHeight, which Closure removed in the advanced build, so that column measured nothing until it was fixed.
  • "Fresh equal maps" scenarios build new map instances with equal content for every update, outside the timed region, like a query doing (map #(assoc % …)). Their hashes are not cached.
  • Renders count render-fn calls; DOM mutations count MutationObserver records (added and removed nodes, attribute and text changes) over one full A ⇄ B cycle, divided by two. Moving one fragment is 4 mutations: marker and row, each removed and added.
  • One machine, one browser. Run-to-run noise is about ±10%, more for sub-microsecond cells. Ratios at n ≤ 3 compare times under 2 µs and should be read as roughly equal unless the gap is large.
  • Release builds skip the duplicate-key check in diff-keyed-seq; dev builds run it on every render.

Re-run: release the :bench-seq build, then node examples/bench-seq/run.mjs. --sizes=1,10,100, --scenarios=swap,shuffle and --json=out.json narrow the run or keep the raw data.

Code, tests and other findings

Correctness

  • 26 node tests with 174 assertions pass in the :node-test build, which also still runs components-test. They cover fixed transitions including duplicates, render counts, preserved DOM nodes for removals, swaps, rotations and scattered updates, and the dev-only duplicate key error.
  • Six fuzz tests run 3000 random transitions each: identity, by value, identity with fresh maps, long lists in both modes, and keyed. The keyed fuzz also checks that no DOM node ever shows a different key than the one it was created for.
  • The tests were checked against deliberately broken versions: with moves disabled, with the wrong anchor for the tail-to-head move, and with render-over enabled in keyed mode. Each one failed the fuzz.

Found along the way

  • sa/destroy! always throws: it calls the p/destroy! protocol method, but TreeRoot only defines destroy! as an Object method.
  • The current keyed-seq seeks moved items with .indexOf from the front, which is quadratic for heavily shuffled lists. The new implementation replaces that path.
